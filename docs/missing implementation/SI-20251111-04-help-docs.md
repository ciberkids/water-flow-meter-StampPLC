## 1. Summary

Expand the Help tab so it thoroughly documents every JSON field, new element type, event binding workflow, scroll bar numbering scheme, and manifest integration. Designers should treat Help as the single source of truth when authoring datasets or troubleshooting validation errors.

---

## 2. Acceptance Criteria

- [ ] Help tab includes sections for schema overview, element reference, animation assets, scroll bar hierarchy numbering, firmware action manifest usage, and Simulation/Design workflows.
- [ ] Examples show valid JSON snippets for each new feature (value placeholders, submenus, scroll bars, events) plus troubleshooting notes for common validation errors.
- [ ] Links/buttons jump from Help to the relevant UI locations (e.g., open Simulation function trace from documentation).
- [ ] Content is accessible (keyboard navigable, screen-reader friendly) and covered by Playwright snapshot tests.

---

## 3. Implementation Notes

- Create structured data (e.g., markdown fragments or JSON descriptors) so Help content stays maintainable.
- Reference the canonical JSON schema to auto-generate parts of the documentation when possible.
- Include diagrams or callouts explaining submenu hierarchy and scroll bar numbering.

---

## 4. Tasks & Checklist

- [ ] Draft expanded Help content covering each requirement bullet.
- [ ] Implement UI components (tabs/accordions) to organize the reference material.
- [ ] Wire contextual links from Help to Simulation/Design panels.
- [ ] Add Playwright snapshots verifying content renders and includes key phrases.
- [ ] Update README/docs to point to the new Help capabilities.

---

## 5. Verification Plan

1. Playwright test to capture Help panel screenshots and assert anchor links navigate correctly.
2. Manual QA to ensure keyboard navigation and screen readers can traverse the content.
3. Schema change cross-check: editing the schema should update Help descriptions (smoke test).

---

## 6. Backout / Fallback Strategy

- Keep legacy Help content accessible via a toggle until the new material stabilizes.
- Store content markdown separately so reverting to the previous revision is straightforward if build/runtime issues surface.
