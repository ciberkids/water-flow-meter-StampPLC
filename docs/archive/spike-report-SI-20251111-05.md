# Spike Report: SI-20251111-05 — Firmware Function Manifest Strategy

**Status:** complete  
**Author:** Matteo  
**Date:** 2026-03-03  
**Feeds into:** SI-20251111-03 (Exporter Schema + Firmware Manifest)

---

## Goal

Identify the best C++ pattern for gathering all UI-callable firmware actions into a JSON manifest so the web exporter tool can validate dataset bindings (e.g. `flow.actionId` references) at export time.

---

## Evaluation Criteria

| Criterion | Weight |
|---|---|
| Minimal boilerplate for adding a new action | High |
| No performance impact on the dispatch hot path | High |
| Maintainability (single source of truth) | High |
| Compatibility with PlatformIO / ESP-IDF | Medium |
| Tooling effort to capture JSON | Medium |

---

## Approach A — Parallel constexpr descriptor table

**Prototype:** `src/ui/sandbox/manifest_spike.cpp`

A second `constexpr` array `kActionDescriptors[]` is defined alongside the existing `kDefaultBindings[]` in `ui_actions.cpp`. Both arrays must stay in the same order. A separate `emitManifestJson()` function iterates the descriptors to produce JSON.

### Pros

- Zero changes to `UiActionRegistry` dispatch code or the existing `UiActionBinding` type.
- `constexpr` arrays are evaluated at compile time — no runtime overhead.
- The descriptor array lives in a separate translation unit if needed; easy to gate behind `#ifdef`.
- Simple, idiomatic C++17.

### Cons

- **Index drift risk:** if a handler is added to `kDefaultBindings` without a matching descriptor, the arrays silently diverge. A `static_assert(kDescriptorCount == kBindingCount)` guard catches this at compile time.
- Developers must update two arrays when adding/removing an action (low risk with the static_assert guard).

---

## Approach B — X-macro single source of truth

**Prototype:** `src/ui/sandbox/manifest_spike_macro.cpp`

A single `UI_ACTION_TABLE(ACTION)` macro lists every action once. Both the dispatch table and the descriptor table are generated by expanding the macro with different `ACTION` definitions.

### Pros

- **Single source of truth** — add one line to the macro table, both dispatch and manifest stay in sync automatically.
- No risk of index drift.

### Cons

- Macro style is unfamiliar to some firmware developers and harder to debug.
- IDE tooling (autocomplete, go-to-definition) struggles with X-macros.
- Mixing macro-generated and hand-written bindings (e.g. for dynamically registered actions) is awkward.
- If the action set ever needs runtime registration, the macro approach breaks down.

---

## Comparison table

| | Approach A (constexpr table) | Approach B (X-macro) |
|---|---|---|
| Boilerplate per new action | 2 array rows + static_assert | 1 macro row |
| Drift protection | `static_assert` | Structural (impossible to drift) |
| IDE support | ✅ Full | ⚠️ Limited |
| Debug-friendliness | ✅ Easy | ⚠️ Harder |
| Runtime registration support | ✅ Yes | ❌ Needs rework |
| Boilerplate for tooling | Low | Low (same emitter) |

---

## Recommendation: **Approach A (constexpr descriptor table)**

Approach A keeps the existing production code structure unchanged, adds a compile-time guard against divergence, and is more maintainable as the firmware grows. The single extra rule for developers ("add a row to `kActionDescriptors` when you add a binding, the static_assert will remind you") is a small and acceptable cost.

### Implementation steps for SI-20251111-03

1. Add `kActionDescriptors[]` and `emitManifestJson()` to `ui_actions.cpp` (or a new `ui_manifest.cpp`).
2. Add a PlatformIO custom script or a dedicated host-side `manifest_gen` binary that calls `emitManifestJson()` and writes `ui_manifest.json` to the project root.
3. Commit the generated `ui_manifest.json` alongside the firmware. The web exporter then reads it via `--manifest`.

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Developer forgets to add descriptor | `static_assert(kDescriptorCount == kBindingCount)` blocks build |
| Manifest goes stale (not re-generated after firmware change) | CI step that runs `manifest_gen` and diffs output; fail if dirty |
| Web tool used against an older manifest | Schema `version` field lets the exporter warn on version mismatch |
